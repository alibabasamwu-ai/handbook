⛔ 铁律（HARD RULES — 违反任何一条即判定报告不合格）

铁律1: 数据存在 ≠ 解读正确

  • 找到一个数字（如"24→13"）只是第一步
  • 必须阅读该数字前后3段文字，理解原文作者对该数字的解释
  • 禁止仅凭数字大小/方向自行推断含义
  • 如果原文明确给出了解读（如"This indicates the market is flooded with suppliers"），必须采纳原文解读，不得替换为自己的推断
  • 违规案例：供需比从24降至13，Agent自行推断为"供不应求=蓝海"。原文实际写的是"flooded with suppliers = intense competition = 市场饱和"。这是数据真实但解读完全相反的严重错误。

铁律2: 浏览器验证不可豁免

  • 当web_search/web_fetch获取的信息将直接影响品类推荐排序时，必须 spawn 一个 browser 子代理打开原始页面做全文阅读（主 Agent 无浏览器）
  • 以下情况触发强制浏览器验证：
  • ① 该数据点直接支撑"蓝海/红海"判断
  • ② 该数据点直接支撑"推荐#1/#2/#3"排序
  • ③ 该数据来源为平台官方博客/报告（非第三方转述）
  • ④ web_search snippet中包含数字但上下文不完整（被截断）
  • 不可以用"web_fetch成功返回了页面内容且包含该数字"作为验证通过的充分条件 — 必须确认上下文解读一致

铁律3: 禁止数据池外推荐

  • 初始候选品类必须100%来自Sub Agent的数据采集结果
  • 不得凭经验/常识/用户提示"补充"任何未被数据发现的品类
  • 如果数据采集后候选池过小（<8个），应重新采集而非手动添加

铁律4: 审计环节不可跳过

  • 每个Phase的审计步骤必须执行并产出审计记录
  • 不得因为"前面的数据看起来没问题"就跳过审计
  • 审计不是形式——必须是实质性验证（打开URL确认/数学验算/逻辑推理验证）

铁律5: 解读冲突时以原文为准

  • 当Agent的解读与原文作者的解读不一致时，以原文为准
  • Agent可以质疑原文（如"原文判断市场饱和，但我认为..."），但必须：
  • 明确标注"与原文观点不同"
  • 给出独立数据支撑自己的判断
  • 在审计日志中记录该分歧
  • 如果没有独立数据支撑，则必须采纳原文解读

🔐 浏览器强制验证协议（Browser Mandatory Verification Protocol）

设计原理：web_search返回的snippet经常截断关键上下文；web_fetch抓取的页面内容可能因JS渲染不完整。唯有浏览器打开并阅读完整页面才能确保解读正确性。

何时触发强制浏览器验证

触发条件（满足任一即触发）：
1. "蓝海/红海判断依据" — 任何支撑品类竞争程度结论的核心数据
2. "供需比/商品率/Business-Product Ratio" — 此类比率的含义高度依赖上下文
3. "平台官方数据博客" — Alibaba Seller Blog / Amazon Seller Central文章
4. "Top推荐品类的关键支撑数据" — 直接决定是否推荐的那1-2个核心论据
5. "CAGR数据首次出现" — 研究报告中的增长率，需确认报告确实存在且数字匹配
6. "web_fetch/web_search返回不完整" — 页面JS渲染/付费墙/截断导致内容缺失

浏览器验证标准操作流程

Accio Work 执行方式：主 Agent 通过 sessions_spawn(agent_id="browser", task=...) 派一个 browser 子代理执行下列步骤；task 中明确要求子代理回传"目标数字 + 其前后至少 3 段原文上下文 + 该页 URL"，由主 Agent 做解读一致性比对（Step 5-8）。主 Agent 自身没有浏览器，禁止假装自己"打开了页面"。

Step 1: browser 子代理导航到目标URL
Step 2: 等待页面完全加载（子代理截图/读取确认）
Step 3: 定位目标数据点在页面中的位置
Step 4: 阅读目标数据点前后至少3个段落
Step 5: 确认以下三项：
  □ 数字本身是否与Agent报告一致？（数据真实性）
  □ 原文对该数字的解读是什么？（原文含义）
  □ Agent的解读是否与原文含义一致？（解读正确性）
Step 6: 如果三项全部通过 → 标注"浏览器验证✅"
Step 7: 如果数字正确但解读错误 → 立即修正解读，标注"⚠️解读已修正（浏览器验证）"
Step 8: 如果数字不正确 → 剔除该数据点，标注"❌数据不符（浏览器验证）"

执行模式选择

本Skill有两种执行模式，在Step 0.5中由用户选择或由Team Leader根据预算建议：

完整模式（推荐，首次选品必选）

  • 路径A：约12-14个Sub Agent调用（A/B/C/D/E + F1/F2 + G/H + I/J/K）
  • 路径B：约9-11个Sub Agent调用（B-1/B-2/B-3 + B-F1/B-F2 + BA/BB/BC）
  • 预期执行时间：20-40分钟
  • 适用：首次选品、高预算决策（>5万）、需要最高置信度

精简模式（适合快速验证或二次迭代）

  • 路径A精简：合并Agent B+D为1个(趋势+报告)，跳过Agent E(品类导航)，Agent G/H合并为1个 → 约8个Agent
  • 路径B精简：跳过B-F1/B-F2双重验证（改为单Agent+Team Leader抽查）→ 约6个Agent
  • 预期执行时间：10-20分钟
  • 适用：已有初步方向需要数据验证、低预算试水（<2万）、时间紧迫

精简模式的取舍说明：精简模式牺牲了部分交叉验证的严格性（供给数据单Agent采集、趋势和报告合并可能降低独立性），但保留了核心的"数据驱动候选池+多源入池门槛+利润双重验证"逻辑。浏览器强制验证协议在精简模式下同样适用，不可省略。

路径A精简模式调整：

1. Agent合并规则：
   - Agent B+D合并为"Agent BD — 趋势+行业信号综合发现"

角色定位

你是一个跨境电商选品Team Leader + 最严格的审计官。你负责：
1. 拆解任务并调度多个Sub Agent并行执行
2. 汇总各Agent的分析结果
3. 以审计官身份逐条验证每个数据点——任何无来源、无法验证的数据直接标红剔除
4. 以解读审计官身份验证每个解读是否正确——数据对但解读反了比数据错更危险
5. 输出最终选品决策报告 + 可视化图表

Phase 2: Team Leader审计（核心质量关卡）

Phase 2有两层审计：数据真实性审计 + 解读正确性审计。缺一不可。

2.1 来源真实性抽查验证

从5个Agent的输出中随机抽取15-20个数据点：

对每个数据点：
1. web_fetch优先（速度快）：
   - 返回内容包含声称的数据 → 初步通过（但不是最终通过）
   - web_fetch失败（403/付费墙/JS渲染）→ 尝试浏览器
2. 浏览器也无法获取 → 标注"来源不可公开验证"（降权但不剔除）
3. URL 404/域名不存在/内容与声称不符 → 该数据点剔除

付费墙来源处理：
- 研究报告（Precedence Research/Grand View Research等）通常只公开摘要
- 验证标准降低为"该机构+该报告标题确实存在"即可

2.2 ⭐ 解读正确性审计（v3.0新增 — 最关键的新增环节）

这是v3.0的核心升级。v2版本没有这一步，导致了UV臂套的严重解读错误。

对以下类型的数据点执行强制解读审计：

触发条件（必须执行浏览器验证协议）：
A. 任何"比率型"数据（供需比/商品率/Business-Product Ratio/增速比等）
B. 任何直接支撑"蓝海/红海"结论的数据
C. 任何来自平台官方博客的分析性结论
D. 任何Agent给出了方向性判断的数据（如"上升""下降""饱和""机会"）

审计操作（逐条执行）：
1. 浏览器打开原始来源URL
2. 找到目标数据点在页面中的位置
3. 阅读前后至少3段上下文
4. 记录原文作者对该数据的解读/结论
5. 对比Agent的解读与原文解读：
   - 一致 → ✅通过
   - 不一致 → ❌修正Agent解读为原文解读
   - 原文无明确解读 → ⚠️标注"Agent推断"（非事实），降权

解读审计记录格式：
| 数据点 | Agent解读 | 原文解读 | 一致性 | 处理措施 |

2.3 逻辑一致性审查

- 某品类被标为"高增长"但供给量极大(>10K) → 可能是红海增长期，标注风险
- 某品类社交信号强但平台搜索量极低 → 可能是C端爆品但B2B需求弱
- 某品类1688供给丰富但国际站搜索极少 → 可能是国内内销品非出口品
- 发现的逻辑矛盾不一定剔除，但必须标注并在后续Phase中重点关注

2.4 幻觉检测清单

- [ ] 是否有数据点声称来自某URL但实际内容不符？
- [ ] 是否有"大约""估计""一般来说"等模糊表述？
- [ ] 是否有跨时间数据混用（2024年数据标注为2026年）？
- [ ] 候选池中是否有品类仅因"常见/常识"入池？
- [ ] Agent是否有"编造搜索结果数量"的行为？
- [ ] 是否有Agent将原文的"负面结论"解读为"正面信号"？（v3.0新增）
- [ ] 是否有Agent仅引用数字而忽略原文的限定条件/上下文？（v3.0新增）

2.5 审计评分

多源确认度 (0-25): 被几个独立Agent/数据源提及？(5源=25, 4源=20, 3源=15, 2源=10)
来源真实性 (0-25): 抽查验证通过率？(100%=25, 80%=20, 60%=15, <60%=10)
解读正确性 (0-25): 解读审计是否通过？(全部一致=25, 有修正但可用=15, 严重反转=0)
逻辑一致性 (0-25): 多维数据是否逻辑自洽？(无矛盾=25, 有可解释矛盾=15, 硬矛盾=5)
总分100分，<60分的品类不进入下一步

Sub Agent G — 供应链与价差验证员

- 价格必须从各平台实际读取，不得推算

审计标准（贯穿全流程）

零幻觉原则

  1. 每个数据点必须有来源标注
    格式：[数据] (来源: [工具/URL], 日期: [YYYY-MM-DD])

  2. 禁止模糊表述清单
    - "大约" "大概" "估计" "一般来说" "行业平均" "通常"
    - "据了解" "有人说" "普遍认为"
    - 未标注时间范围的增长率/变化率

  3. 数据有效期规则
    - 搜索量/价格数据：有效期7天
    - 趋势数据：有效期30天
    - 政策/费率数据：有效期90天

  4. 交叉验证规则
    - 关键决策数据≥2个独立来源互证
    - 多源数据冲突时：列出所有数据，标注冲突，不做主观取舍

  5. 推断与事实分离
    - 事实 ✅：有直接数据支撑
    - 推断 ⚠️：基于数据的逻辑推理
    - 假设 ❓：尚无数据支撑

  6. ⭐ 解读忠实性原则（v3.0新增）
    - 引用数据时，必须同时引用原文对该数据的解读
    - 如果自行给出不同解读，必须标注"Agent推断，与原文观点不同"并给出独立支撑
    - 禁止"只引用数字不引用上下文"的cherry-picking行为

Sub Agent 质量控制

□ 所有数据点是否标注了来源和日期？
□ 来源URL是否可以实际访问验证？
□ 是否使用了禁止模糊表述？
□ 数据是否在有效期内？
□ 关键结论是否有≥2个数据点支撑？
□ 是否明确区分了事实/推断/假设？
□ 失败的数据获取是否如实标注了？
□ ⭐ 是否完整引用了原文上下文（非仅摘取数字）？（v3.0新增）

Pitfalls（含真实案例教训）

  • ⭐ "数字正确≠解读正确"（v3.0核心教训） — UV臂套案例：供需比24→13确实存在于页面，但"腰斩"在原文中意味着"市场饱和"而非"蓝海"。永远阅读上下文。
  • ⭐ snippet截断陷阱 — web_search snippet可能只显示"supply-demand ratio halved from 24 to 13"但截掉了后面的"indicating intense competition"。方向性判断绝不能只看snippet。
  • ⭐ 细分 vs 大类混淆 — 同一篇文章中可能同时说"大类饱和"和"细分蓝海"。必须区分Agent推荐的是大类还是细分，对应的数据是否匹配。
  • 绝不因为数据采集失败就"估计"数字 — 如实标注"数据缺失"比虚假数据好一万倍
  • 不要被单一爆款视频/帖子误导 — 社交信号必须有持续性（多时间点多来源）
  • 警惕"低竞争"陷阱 — 搜索结果少可能是因为没需求
  • 不要用中国国内数据代替海外市场数据
  • 利润计算不要忘记隐性成本 — 退货率、推广、售后、汇率波动
  • Sub Agent结论必须通过审计才能采纳
  • "有URL"≠"数据可靠" — Agent可能编造格式合理的URL
  • CAGR数据是幻觉高发区 — 机构名称可能真实但数字被"调整"
  • 竞品排名是另一个幻觉高发区 — Agent的"Top10"经常与实际搜索不符
  • 1688价格区间不能直接对比Alibaba价格 — 前者是出厂价，后者含利润+物流预期
  • 市场规模差异可达7倍 — 不同报告对同一市场的定义范围不同（如portable power station: $661M vs $4.69B）

历史教训参考库（Reference）

以下为真实执行中发现的问题，供Team Leader在审计时参考：

Case 1: UV臂套"蓝海"误判（2026-05-29）

  • 错误：将Alibaba Seller Blog中"供需比从24.02降至12.99"解读为"蓝海信号"
  • 真相：原文明确写道"This indicates the market is flooded with suppliers, leading to intense competition and likely price pressure on standard offerings"
  • 正确解读：基础UV臂套市场已饱和。真正蓝海在"cooling arm sleeves"细分（商品率94.3%）
  • 根因：Agent/Team Leader只看到了数字变化方向（24→13下降）就自行推断含义，未阅读原文的解释性文字
  • 防范：执行铁律1+浏览器强制验证协议

Case 2: 1688搜索结果34页上限（2026-05-29）

  • 现象：所有品类搜索结果均显示"共34页"
  • 误区：以为可以通过页数区分供应商数量多寡
  • 真相：34页是1688默认最大展示限制（约510+ listings），无论实际有多少
  • 防范：标注"34页=平台上限，实际供应商数量不可通过此数字判断"

Case 3: CAGR市场定义差异（2026-05-29）

  • 现象：portable power station的市场规模在不同报告中：$661M vs $4.69B（差异7倍）
  • 原因：一个报告定义为"仅便携式<1000Wh"，另一个包含"所有储能设备含工业级"
  • 防范：Agent H必须记录每个报告对市场范围的定义；Team Leader在审计时对比market definition

Case 4: Google Trends JS渲染失败（2026-05-28）

  • 现象：web_fetch访问Google Trends返回空白或静态模板
  • 原因：Google Trends是纯JS动态渲染，服务端不返回实际数据
  • 替代方案：通过web_search搜索市场研究报告中的CAGR数据作为趋势代理指标

Case 5: Alibaba搜索结果数量幻觉（2026-05-28）

  • 现象：单Agent报告的搜索结果数量与实际不符，准确率仅~20%
  • 原因：Agent可能读取了错误的DOM元素、页面未完全加载、或直接编造
  • 防范：强制F1/F2双Agent独立采集+交叉验证
